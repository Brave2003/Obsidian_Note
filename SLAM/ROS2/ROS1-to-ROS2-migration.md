# 第 3 章：从 ROS1 到 ROS2 的迁移策略

在前两章中，我们回顾了 ROS1 的核心架构并深入分析了其在实际工业应用中暴露的局限性。本章将聚焦于实际的迁移策略，为那些需要将现有 ROS1 系统升级到 ROS2 的团队提供系统化的指导。迁移不仅仅是代码层面的改写，更涉及架构设计、性能优化、团队协作等多个维度的考量。我们将通过 Toyota HSR 的实际迁移案例，展示如何在保证系统稳定性的前提下，逐步完成这一复杂的工程任务。

---

## 3.1 迁移评估与决策框架

在开始任何迁移工作之前，首要任务是全面评估现有系统并制定合理的迁移策略。

### 3.1.1 系统复杂度评估矩阵

```
复杂度评分 = α·节点数量 + β·自定义消息类型 + γ·外部依赖 + δ·实时性要求
```

其中权重系数 α=0.2, β=0.3, γ=0.3, δ=0.2 是基于工业实践的经验值。

**为什么自定义消息和外部依赖的权重更高？**
- 自定义消息迁移需要修改 `.msg` → `.idl`，且 ROS2 消息命名空间不同（`msg/` 前缀），可能涉及字段类型变更
- 外部依赖是最不可控的——你无法控制第三方库何时支持 ROS2，这会阻塞整个迁移
- 节点数量虽然大但迁移模式固定（逐个改写），风险可控

### 3.1.2 迁移收益分析

迁移到 ROS2 的主要收益包括：

1. **实时性提升**：DDS 中间件支持确定性通信，延迟可预测性提升 10 倍
2. **安全性增强**：SROS2 提供端到端加密，满足 ISO 26262 功能安全要求
3. **可扩展性改善**：去中心化架构消除 Master 单点故障，支持 1000+ 节点集群
4. **生命周期管理**：标准化的节点状态机，简化复杂系统的启动和关闭流程
5. **长期维护**：ROS1 Noetic 2025年 EOL，社区全面转向 ROS2

### 3.1.3 风险评估清单

- 第三方包依赖的 ROS2 支持情况
- 团队的 Modern C++ (C++14/17) 掌握程度
- 实时性测试基础设施的完备性
- 回滚方案的可行性

## 3.2 ros1_bridge 桥接方案

ros1_bridge 是官方提供的 ROS1 和 ROS2 互操作性解决方案，它允许两个版本的节点在同一系统中共存并相互通信。

### 3.2.1 桥接架构原理

ros1_bridge 本质上是一个双向协议转换器，同时运行 ROS1 和 ROS2 的客户端库：

```
     ROS1 Domain                    ROS2 Domain
    ┌──────────┐                  ┌──────────┐
    │ ROS1 Node│                  │ ROS2 Node│
    └─────┬────┘                  └────┬─────┘
          │                             │
    ┌─────▼──────────────────────────▼─────┐
    │          ros1_bridge                  │
    │  ┌─────────────┐  ┌─────────────┐   │
    │  │  ROS1 Client│  │  ROS2 Client│   │
    │  └──────────────┘  └──────────────┘  │
    │         │                 │          │
    │    ┌────▼─────────────────▼────┐    │
    │    │   Message Type Mapping    │    │
    │    └───────────────────────────┘    │
    └───────────────────────────────────────┘
```

### 3.2.2 消息类型映射机制

三种映射模式：

1. **直接映射**：字段名称和类型完全一致（如 `std_msgs/String`）
2. **规则映射**：通过 YAML 配置文件定义字段转换规则
3. **自定义映射**：编写 C++ 转换函数处理复杂逻辑

### 3.2.3 性能特性与优化

桥接器性能开销：
- 序列化/反序列化：~10-20 μs/消息（1KB payload）
- 类型转换：~5-15 μs（取决于映射复杂度）
- 上下文切换：~20-30 μs（ROS1/ROS2 事件循环切换）
- **总计：~35-65 μs/消息**

优化策略：
- **批量传输**：聚合多个小消息减少开销
- **延迟订阅**：仅在有订阅者时才建立桥接
- **QoS 匹配**：合理配置 DDS QoS 减少重传

### 3.2.4 动态桥接与静态桥接

**动态桥接**（默认）：运行时自动发现需要桥接的话题——灵活但有性能开销，适合开发/测试。

**静态桥接**（推荐生产环境）：预指定需要桥接的接口——性能更优、行为可预测。

```bash
ros2 run ros1_bridge parameter_bridge \
  /cmd_vel@geometry_msgs/msg/Twist@geometry_msgs/Twist \
  /scan@sensor_msgs/msg/LaserScan@sensor_msgs/LaserScan
```

## 3.3 代码移植最佳实践

### 3.3.1 核心 API 对照表

| ROS1 API | ROS2 API | 主要差异 |
|----------|----------|---------|
| `ros::init()` | `rclcpp::init()` | 支持多实例 |
| `ros::NodeHandle` | `rclcpp::Node` | 节点成为一等公民 |
| `ros::Publisher` | `rclcpp::Publisher<T>` | 强类型模板 |
| `ros::Subscriber` | `rclcpp::Subscription<T>` | 智能指针管理 |
| `ros::ServiceServer` | `rclcpp::Service<T>` | 类型安全增强 |
| `ros::Rate` | `rclcpp::Rate` | 支持多种时钟源 |
| `ros::Time::now()` | `node->now()` | 时间与节点关联 |
| `ros::param::get()` | `node->declare_parameter()` | 参数需要声明 |

### 3.3.2 编程范式转变

**ROS1 函数式风格**：

```cpp
void callback(const std_msgs::String::ConstPtr& msg) {
    ROS_INFO("I heard: [%s]", msg->data.c_str());
}
int main(int argc, char** argv) {
    ros::init(argc, argv, "listener");
    ros::NodeHandle n;
    ros::Subscriber sub = n.subscribe("chatter", 1000, callback);
    ros::spin();
}
```

**ROS2 面向对象风格**：

```cpp
class MinimalSubscriber : public rclcpp::Node {
public:
    MinimalSubscriber() : Node("minimal_subscriber") {
        subscription_ = this->create_subscription<std_msgs::msg::String>(
            "topic", 10,
            std::bind(&MinimalSubscriber::callback, this, std::placeholders::_1));
    }
private:
    void callback(const std_msgs::msg::String::SharedPtr msg) {
        RCLCPP_INFO(this->get_logger(), "I heard: '%s'", msg->data.c_str());
    }
    rclcpp::Subscription<std_msgs::msg::String>::SharedPtr subscription_;
};
```

### 3.3.3 参数系统迁移

**为什么 ROS2 要求 `declare_parameter`？**

ROS1：运行时动态获取，无需声明 → 灵活但不可预测
ROS2：必须先声明再获取 → 类型安全、自文档化、支持参数验证和变更回调

```cpp
// ROS1 - 运行时动态获取
double param;
nh.param<double>("my_param", param, 1.0);

// ROS2 - 需要先声明
this->declare_parameter("my_param", 1.0);
double param = this->get_parameter("my_param").as_double();

// ROS2 - 参数变更回调
auto param_callback = [this](const std::vector<rclcpp::Parameter>& params) {
    for (const auto& param : params) {
        if (param.get_name() == "my_param") {
            // 处理参数更新
        }
    }
    return rcl_interfaces::msg::SetParametersResult();
};
this->add_on_set_parameters_callback(param_callback);
```

## 3.4 工具链对比（catkin vs colcon）

### 3.4.1 构建系统架构对比

**Catkin (ROS1)**：基于 CMake 的元构建系统，强制特定工作空间布局，所有包共享同一个 CMake 上下文。

**Colcon (ROS2)**：通用构建工具，支持多种构建系统，每个包独立构建——并行度更高、隔离更好。

```
Catkin 工作空间:                    Colcon 工作空间:
workspace/                          workspace/
├── src/                           ├── src/
│   ├── package1/                  │   ├── package1/
│   └── package2/                  │   └── package2/
├── build/        (共享)            ├── build/
├── devel/        (开发空间)        │   ├── package1/  (独立)
└── install/      (可选)            │   └── package2/  (独立)
                                   ├── install/
                                   └── log/          (构建日志)
```

### 3.4.2 构建命令对比

| 操作 | Catkin (ROS1) | Colcon (ROS2) |
|------|-------------|--------------|
| 构建所有包 | `catkin_make` | `colcon build` |
| 构建单个包 | `catkin_make --pkg <pkg>` | `colcon build --packages-select <pkg>` |
| 清理构建 | `catkin_make clean` | `rm -rf build install log` |
| 并行构建 | `catkin_make -j4` | `colcon build --parallel-workers 4` |
| 符号链接安装 | `catkin_make install` | `colcon build --symlink-install` |

### 3.4.3 CMakeLists.txt 关键变化

- ROS1: `find_package(catkin ...)` + `catkin_package()`
- ROS2: `find_package(ament_cmake ...)` + `ament_package()`
- 消息生成: `add_message_files()` → `rosidl_generate_interfaces()`
- 依赖: `target_link_libraries(... ${catkin_LIBRARIES})` → `ament_target_dependencies(...)`

## 3.5 渐进式迁移路线图

渐进式迁移是大型机器人系统从 ROS1 过渡到 ROS2 的推荐策略。

### 迁移五阶段

| 阶段 | 周期 | 核心任务 |
|------|------|---------|
| Phase 1: 评估与准备 | 2-4周 | 依赖分析、基准建立、团队培训 |
| Phase 2: 基础设施迁移 | 4-8周 | 消息定义、构建系统、工具库迁移 |
| Phase 3: 感知模块迁移 | 6-12周 | 传感器驱动优先、逐节点替换 |
| Phase 4: 控制与规划迁移 | 8-16周 | 实时性验证、故障注入测试 |
| Phase 5: 系统集成与优化 | 4-8周 | 移除bridge、QoS优化、文档完善 |

### 混合系统架构设计

```
┌─────────────────────────────────────────────────┐
│                  System Monitor                  │
│              (ROS2 Lifecycle Manager)            │
└─────────────┬───────────────────────────────────┘
              │
    ┌─────────▼─────────┐       ┌─────────────────┐
    │   Perception       │       │    Planning     │
    │   (ROS2 Domain)    │◄─────►│  (ROS1 Domain)  │
    └─────────┬─────────┘bridge └────────┬────────┘
              │                           │
    ┌─────────▼─────────────────────────▼────────┐
    │              Hardware Abstraction           │
    │                 (ROS2 Native)              │
    └─────────────────────────────────────────────┘
```

### 数据流迁移策略

最小化桥接原则：
1. 识别高频数据流，优先迁移整条管道
2. 避免数据在 ROS1 和 ROS2 间多次往返
3. 使用共享内存减少大数据传输开销

```
原始架构 (纯 ROS1):
Camera → ImageProc → Detection → Tracking → Planning

过渡架构 (混合):
Camera(ROS2) → Bridge → ImageProc(ROS1) → Detection(ROS1) → Bridge → Planning(ROS2)
(性能损失: 2次桥接)

优化架构 (批量迁移):
Camera(ROS2) → ImageProc(ROS2) → Detection(ROS2) → Bridge → Planning(ROS1)
(性能损失: 1次桥接)
```

## 3.6 产业案例研究：Toyota HSR 机器人迁移经验

Toyota Human Support Robot (HSR) 是服务机器人领域的标杆产品，其从 ROS1 到 ROS2 的迁移过程为业界提供了宝贵经验。

### 系统规模

- 节点数量：**120+** 个活跃节点
- 代码规模：**50 万行** C++/Python 代码
- 第三方依赖：**30+** 个外部库
- 硬件接口：**20+** 种传感器和执行器

### 迁移策略："核心先行，边缘跟进"

**第一批迁移（3个月）——硬件抽象层**：
选择理由：直接受益于 ROS2 实时性改进，减少后续迁移的接口变更

**第二批迁移（6个月）——感知管道**：
优化成果：点云处理延迟降低 40%（零拷贝传输），GPU 加速节点直接集成

**第三批迁移（9个月）——任务规划与执行**：
技术难点：MoveIt1 到 MoveIt2 API 大幅变化，自定义规划器插件需要重写

### 技术亮点

**1. 双模式运行架构**：允许机器人在 ROS1/ROS2/HYBRID 三种模式间运行时切换——"白班用 ROS1 保障生产，夜班切 HYBRID 测试 ROS2 组件"。

**2. 性能监控与自动降级**：连续 10 次控制抖动 > 2ms 自动降级到 ROS1，用数据驱动决策而非依赖人的判断。

**3. 零拷贝桥接**：针对高频关节状态（1kHz）使用共享内存 TypeAdapter，桥接延迟降至 <5μs。

### 性能对比

| 指标 | ROS1 基线 | ROS2 优化后 | 改进幅度 |
|------|----------|-----------|---------|
| 控制循环频率 | 500 Hz (±50Hz) | 1000 Hz (±10Hz) | **+100%** |
| 点云传输延迟 | 45ms | 12ms | **-73%** |
| 系统启动时间 | 120s | 35s | **-71%** |
| 内存占用 | 4.2 GB | 3.1 GB | **-26%** |
| CPU 使用率（空闲） | 35% | 22% | **-37%** |
| 网络带宽（局域网） | 850 Mbps | 320 Mbps | **-62%** |

### 经验教训

**成功因素**：
1. 充分的测试覆盖（迁移前 85%）
2. 渐进式迁移——避免"大爆炸"
3. 性能基准先行——建立量化对比基础
4. 提前 3 个月开始 ROS2 培训

**踩坑经历**：
1. QoS 不匹配——早期因配置不当导致消息"静默丢失"
2. 时间同步——从 `/clock` 话题到 `use_sim_time` 参数的迁移极其容易出错
3. 构建时间——初期 colcon 是 catkin 的 2 倍
4. 文档滞后——TypeAdapter 等新特性需要读源码

## 3.7 高级话题：零停机迁移与灰度发布策略

### 3.7.1 蓝绿部署架构

```
┌─────────────────────────────────────────────┐
│            Load Balancer / Router           │
│         (Topic-based Traffic Control)       │
└──────────────┬─────────────┬────────────────┘
               │     70%     │    30%
     ┌─────────▼────────┐   ▼──────────────┐
     │   Blue System    │   │  Green System  │
     │   (ROS1 Stable)  │   │  (ROS2 Testing)│
     └──────────────────┘   └───────────────┘
               │                    │
     ┌─────────▼────────────────────▼────────┐
     │         Shared Hardware Layer          │
     └────────────────────────────────────────┘
```

### 3.7.2 金丝雀发布

逐步将流量从 ROS1 切换到 ROS2：1% → 10% → 50% → 100%，每一步监控关键指标，检测到异常立即回滚。

**为什么逐步切换？** 如果 ROS2 系统有未检测到的 bug，100% 流量切换意味着 100% 的故障影响。从 1% 开始即使出问题也只影响 1% 的流量。

### 3.7.3 流量镜像与验证

将生产流量异步镜像到 ROS2 系统，对比两个系统的输出——发现差异但不影响生产。当 ROS2 一致性率达到 99.9% 以上时，切换。

### 3.7.4 状态同步机制

模式切换不仅仅是"杀进程+启进程"，需要先保存系统当前状态（机器人位姿、关节状态等），在新模式下恢复，避免"定位丢失"。

### 3.7.5 回滚策略与断路器

**断路器模式**是防御性设计：不仅仅是"ROS2 出错时用 ROS1"，而是防止快速反复切换（flapping）。冷却期确保 ROS2 有时间恢复。

```
CLOSED ──连续失败N次──→ OPEN
  ↑                        │
  │                  冷却时间后
  │                        ↓
CLOSED ←──成功── HALF_OPEN
```

## 3.8 本章小结

### 核心概念回顾

1. **迁移决策框架**：基于系统复杂度、实时性需求、安全要求等多维度评估
2. **桥接技术**：ros1_bridge 提供渐进式迁移的技术基础，性能开销可控（~50μs/msg）
3. **API 迁移模式**：从函数式到面向对象、更严格的类型系统、生命周期管理标准化
4. **构建系统差异**：Catkin → Colcon，更灵活的工作空间管理、更强并行构建
5. **渐进式路线图**：5 阶段、24-48 周，始终保留回退能力

### 迁移时间线参考

- 小型系统（<20节点）：2-3 个月
- 中型系统（20-100节点）：6-9 个月
- 大型系统（>100节点）：12-18 个月

### 实践经验总结

1. **渐进式迁移优于大爆炸式迁移**：降低风险、允许逐步验证
2. **性能基准先行**：建立量化对比基础——不能靠"感觉"判断迁移是否成功
3. **双模式运行架构**：提供回滚能力和 A/B 测试环境
4. **自动化测试覆盖**：迁移前至少 85% 覆盖率——这不是目标，是最低要求

## 3.9 练习题

### 基础理解题

**练习 3.1**：解释 ros1_bridge 的工作原理，并说明为什么需要消息类型映射。

> [!faq]- 📝 参考答案
>
> ros1_bridge 是一个双栈节点，同时运行 ROS1 和 ROS2 客户端库。它订阅一侧的消息，进行反序列化，转换数据格式，再序列化并发布到另一侧。
>
> **为什么需要消息类型映射？**
> 1. ROS2 消息使用 IDL 定义，命名空间不同（`geometry_msgs/Twist` vs `geometry_msgs/msg/Twist`）
> 2. 某些字段类型发生变化（如时间戳 `ros::Time` → `builtin_interfaces/msg/Time`）
> 3. ROS2 支持更丰富的类型系统（如 bounded sequences、wstring）
> 4. 自定义消息的字段可能在两个版本间不兼容——需要显式的转换规则

---

**练习 3.2**：列举三个 ROS2 相比 ROS1 在 API 层面的主要改进。

> [!faq]- 📝 参考答案
>
> 1. **强类型模板化接口**：`Publisher<MessageType>` 确保编译时类型检查。ROS1 的 `advertise<MsgType>` 只在运行时关联类型——类型不匹配是运行时错误。ROS2 的模板化设计将错误提前到编译期。
>
> 2. **RAII 资源管理**：使用智能指针自动管理生命周期。ROS1 中 `ros::Publisher` 的析构可能触发网络调用（deregister），时序不确定。ROS2 的 `SharedPtr` 模式消除了手动资源管理。
>
> 3. **Executor 模型**：ROS1 的 `ros::spin()` 是全局单线程。ROS2 的 Executor 支持多线程、可组合多个节点到一个 Executor。这意味着你可以控制回调的并发度——单线程 Executor 保证回调不并发，多线程 Executor 利用多核。

---

**练习 3.3**：比较 catkin_make 和 colcon build 的构建策略差异。

> [!faq]- 📝 参考答案
>
> catkin_make 使用单一 CMake 上下文——所有包共享同一个构建空间。这意味着一个包的编译错误会影响整个构建（即使该包与你的修改无关）。依赖通过拓扑排序自动决定构建顺序。
>
> colcon build 为每个包独立构建——提供更好的隔离性。colcon 的 key insight 是"包是独立的构建单元"：每个包有自己的 build/ 目录、自己的 CMake 调用、自己的编译日志。好处是：
> - 一个包的构建失败不影响其他包的持续构建
> - 并行度更高（独立的 CMake 调用可以完全并行）
> - 支持多种构建系统（CMake、Python setuptools、Cargo 等）
> - 增量构建更精确（只重编译真正变化的包）

### 实践应用题

**练习 3.4**：设计一个混合系统架构，其中感知模块使用 ROS2，而规划模块仍使用 ROS1。

> [!faq]- 📝 参考答案
>
> **核心原则**：将高频传感器数据（激光 40Hz、相机 30Hz）在 ROS2 域内处理完成，仅将处理后的感知结果（障碍物列表、语义地图——通常 10-20Hz，<100KB）通过 bridge 传递给 ROS1 规划模块。
>
> **为什么这样设计？** 避免原始传感器数据的频繁桥接。原始激光扫描（40Hz × 2KB）和图像（30Hz × 6MB）如果每次都要经过 bridge，延迟积累和带宽浪费是灾难性的。感知模块通常是计算密集但接口简单——输出是结构化的检测结果，输入是原始传感器流。把计算密集部分放在 ROS2 侧利用 DDS 的零拷贝能力，只把最终结果（数据量小 100-1000x）桥接到 ROS1。

---

**练习 3.5**：编写一个 Python 脚本，自动分析 ROS1 包的依赖关系，并生成迁移优先级列表。

> [!faq]- 📝 参考答案
>
> **算法思路**：
> 1. 递归解析所有 `package.xml` 文件，提取 `<depend>`、`<build_depend>`、`<exec_depend>` 标签
> 2. 构建有向无环图（DAG）——节点是包，边表示"依赖"
> 3. 识别叶节点（无其他包依赖的包）作为优先迁移目标——它们不阻塞任何下游包
> 4. 使用拓扑排序生成迁移顺序
>
> **为什么拓扑排序？** 如果包 A 依赖包 B，你必须先迁移 B（或者至少用 bridge 桥接 B 的接口）。反转这个依赖图就得到了安全的迁移顺序：数据驱动的节点（如传感器驱动）通常在最底层，业务逻辑节点在顶层。从底层开始迁移意味着上层节点可以通过 bridge 继续工作直到被迁移。

### 开放思考题

**练习 3.6**：某公司的物流机器人系统有 50 个 ROS1 节点，需要在不影响日常运营的情况下迁移到 ROS2。设计一个为期 6 个月的迁移计划。

> [!faq]- 📝 参考答案
>
> | 月份 | 阶段 | 关键活动 |
> |------|------|---------|
> | 1-2 | 环境准备 | 团队培训、建立性能基准、迁移基础库和消息定义 |
> | 3 | 硬件抽象层 | 迁移硬件驱动（传感器/电机），使用 bridge 保持上层兼容 |
> | 4 | 定位与建图 | 迁移 SLAM 模块，shadow mode 验证一致性 |
> | 5 | 导航与规划 | 迁移 move_base + 规划器，A/B 测试 |
> | 6 | 系统优化 | 移除 bridge，QoS 调优，文档完善 |
>
> **关键风险点**：
> - **第三方库兼容性**：特别是 move_base 这类核心导航包的 ROS2 版本 (Nav2) API 完全不同——这不是简单移植，而是重写
> - **实时性退化**：迁移到 ROS2 后控制频率反而下降是最常见的初期问题——通常是 QoS 配置不当（RELIABLE vs BEST_EFFORT）
> - **团队学习曲线**：50 节点的迁移需要团队中至少 2-3 人对 ROS2 有深入理解
>
> **验证策略**：每阶段设置量化指标（延迟 P99、消息丢失率、CPU/内存），保持双系统并行运行能力。如果任何指标退化 > 20%，该阶段的迁移暂时回滚。

**练习 3.7**：讨论在云机器人场景下，ROS1 到 ROS2 迁移可能带来的额外挑战和机遇。

> [!faq]- 📝 参考答案
>
> **挑战**：
> 1. **DDS 发现跨 NAT**：DDS 的 Simple Discovery Protocol 依赖组播 UDP——在云环境（跨 NAT/VPC）中组播不可用。需要配置 Discovery Server 或使用 RTPS 单播发现
> 2. **广域网延迟**：DDS QoS 的默认配置为局域网优化（微秒级重传超时），在 WAN 环境（50-200ms RTT）下需要大幅调整
> 3. **大规模域管理**：1000+ 节点的云机器人集群需要仔细规划 DDS Domain ID 和 Partition 的划分
>
> **机遇**：
> 1. **DDS Security** 提供端到端加密——在云场景中这是必须的
> 2. **QoS 策略**（DEADLINE、LIFESPAN）天然支持"过期数据自动丢弃"——对云端的延迟容忍通信非常有用
> 3. **去中心化架构**天然适合边缘计算——机器人端可以独立运行，与云的连接断开不影响本地功能
> 4. **多种 DDS 实现**可选择针对特定场景优化的版本（如 RTI Connext 针对大规模、CycloneDDS 针对嵌入式）

**练习 3.8**：评估使用容器化（Docker/Kubernetes）技术辅助 ROS1 到 ROS2 迁移的可行性。

> [!faq]- 📝 参考答案
>
> **容器化方案**：
> 1. 将 ROS1 和 ROS2 节点分别打包到不同容器——环境完全隔离，不存在 ROS1 和 ROS2 的依赖冲突
> 2. 使用 host 网络模式确保 DDS 发现（DDS 需要访问真实的网络接口进行组播）
> 3. 通过 Kubernetes ConfigMap 管理配置，支持快速在 ROS1/ROS2 间切换
> 4. 通过 Rolling Update 实现渐进式部署——逐个 Pod 从 ROS1 升级到 ROS2
>
> **为什么 host 网络模式？** Docker 默认的 bridge 网络会做 SNAT，导致 ROS 节点看到的是 NAT 后的 IP——在 ROS1 中这会破坏节点发现（XMLRPC 交换的是真实 IP），在 ROS2 中会破坏 DDS 发现（组播包被 bridge 隔离）。host 网络模式是解决此问题的最简单方案。
>
> **优势**：环境隔离、快速回滚（`kubectl rollout undo`）、资源控制（CPU/Memory limits）
> **挑战**：硬件设备访问需要 `--privileged` 或 device plugins、实时性能受容器化开销影响（但 < 5%）、网络配置复杂性

## 3.10 常见陷阱与错误

### 陷阱 1：忽视 QoS 兼容性
**问题**：ROS2 节点间 QoS 设置不匹配导致无法通信——消息没有报错，只是收不到。
**解决**：使用 `ros2 topic info -v` 查看 QoS 设置，确保发布者和订阅者兼容（RELIABLE 必须配 RELIABLE，KEEP_LAST 的 depth 要匹配）。

### 陷阱 2：时间源混淆
**问题**：ROS1 使用 `/clock` 话题，ROS2 使用参数 `use_sim_time`。
**解决**：统一配置时间源，bridge 需要特殊处理时间同步。

### 陷阱 3：参数服务架构差异
**问题**：ROS1 全局参数服务器，ROS2 节点本地参数——迁移后参数无法跨节点共享。
**解决**：使用参数事件机制或专门的参数管理节点。

### 陷阱 4：消息定义不兼容
**问题**：相同名称的消息在 ROS1 和 ROS2 中字段不同。
**解决**：创建自定义映射规则或统一消息定义。

### 陷阱 5：构建系统缓存问题
**问题**：colcon 缓存导致修改未生效。
**解决**：使用 `--cmake-clean-cache` 或删除 `build/install` 目录。

### 陷阱 6：DDS 域 ID 冲突
**问题**：多个 ROS2 实例使用相同域 ID，接收到非预期的消息。
**解决**：通过 `ROS_DOMAIN_ID` 环境变量隔离。

### 陷阱 7：生命周期节点状态不一致
**问题**：节点状态转换失败但系统继续运行，部分功能不可用且日志无明显错误。
**解决**：实现状态监控和自动恢复机制。

### 陷阱 8：内存泄漏在长时间运行
**问题**：bridge 或转换代码存在内存泄漏，系统运行数小时后性能下降。
**解决**：使用 valgrind 或 AddressSanitizer 检测。
